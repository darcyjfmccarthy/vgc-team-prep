# Domain and data specification

## Modeling conventions

- Primary keys are UUIDv7 generated by the application.
- Timestamps are UTC `timestamptz`; the UI localizes them.
- Every private aggregate root carries `user_id`. Child tables reach an owned root by a foreign key; queries always scope through that root.
- User-facing deletion uses `deleted_at` where recovery or references matter. Account purge physically removes/anonymizes records according to the retention policy.
- Enums use checked text values where deployments must add values without PostgreSQL enum migrations.
- Flexible source payloads may use JSONB; core queryable facts use typed columns/tables.
- Normalized text has a retained raw counterpart at ingestion boundaries.
- Derived rows carry source/parser/engine/catalog versions and `computed_at`.

## Core entities and tables

This is the logical schema. Exact indexes and constraint names belong in migrations.

### Identity

`users`

- `id`, `email_normalized` (unique), `password_hash`, `display_name`
- `created_at`, `updated_at`, `deletion_requested_at`, `deleted_at`

`sessions`

- `id`, `user_id`, `token_hash` (unique), `created_at`, `last_seen_at`, `idle_expires_at`, `absolute_expires_at`, `revoked_at`
- The opaque token exists only in the secure cookie; the database stores its cryptographic hash.

`password_reset_tokens`

- `id`, `user_id`, `token_hash` (unique), `expires_at`, `used_at`, `created_at`
- Issuing a newer token invalidates outstanding tokens according to the authentication policy.

P1 `external_identities` links a provider and provider subject to an existing `user_id`; it does not replace the application user record.

`showdown_aliases`

- `id`, `user_id`, `username_display`, `username_normalized`, `is_default`, timestamps
- Unique `(user_id, username_normalized)`; never globally unique and never verified.

### Catalog and rules

`catalog_versions`: `id`, semantic/version label, source metadata, checksum, effective dates.

`species`, `forms`, `moves`, `items`, `abilities`, `natures`: stable internal IDs and canonical slugs. Display labels and mechanics attributes live in versioned companion tables keyed by catalog version.

`rulesets`: `id`, canonical slug, display name, generation/game, team size, bring size, level rules, mechanics configuration, active state, catalog version.

`external_id_mappings`: provider, entity kind, provider identifier, canonical entity ID, mapping confidence/provenance.

### Teams

`teams` (persistent identity)

- `id`, `user_id`, `title`, `description`, `status`, `created_at`, `updated_at`, `archived_at`, `deleted_at`
- Status P0: `active | testing | archived`.

`team_versions` (immutable competitive snapshot)

- `id`, `team_id`, monotonically increasing `version_number`, `ruleset_id`, `catalog_version_id`
- `change_summary`, `source_kind`, `source_text`, `created_at`, `sealed_at`
- Unique `(team_id, version_number)`.
- A version is mutable only while `sealed_at IS NULL`. Any historical/dependent reference atomically seals it.

`team_slots`

- `id`, `team_version_id`, `slot_number` 1–6, `slot_identity_id`, `species_id`, nullable `form_id`
- nickname, gender, level, item, ability, nature, supported-mechanics JSON validated by ruleset
- Unique `(team_version_id, slot_number)`.

`slot_identities` provide logical continuity for “the same slot/Pokémon” across versions. They belong to a team and are explicitly mapped during version creation; species replacement normally creates a new slot identity unless the user confirms continuity.

`team_slot_moves`: slot, ordinal, move ID. `team_slot_evs`: slot plus six non-negative stats with ruleset-aware totals. IVs are not stored.

`tags` and `tag_assignments`: user-owned normalized label/color and typed subject reference. P1 organization adds `collections` and `collection_memberships` for folder/event/season/project.

### Replay ingestion and battles

`replay_import_batches`

- `id`, `user_id`, requested team/version, requested alias/player side, status, total/success/error counts, timestamps.

`replay_import_items`

- `id`, batch, original URL, canonical URL, provider, provider replay ID, status/error code/error detail, existing game ID, timestamps.
- Unique `(user_id, provider, provider_replay_id)` for idempotency where the provider ID is trustworthy.

`replay_sources`

- `id`, provider/replay ID, canonical URL, exact raw `bytea` content, content checksum, content type/encoding, retrieved at, HTTP/source metadata, retention state.
- Raw content is stored in PostgreSQL initially and is never logged. If measurements later require object storage, this table retains checksum/location/provenance while the domain relationship remains unchanged.

`games`

- `id`, `user_id`, `replay_source_id`, `parser_run_id`, `ruleset_id`, `team_id`, exact nullable `team_version_id`
- timestamp, player sides/names, selected user side, winner side, effective result (`win | loss | tie | unknown`)
- format context (`bo1 | bo3 | unknown`), ladder rating, sheet state (`open | closed | unknown`)
- import status, created/updated/deleted timestamps.

`parser_runs`

- `id`, replay source, parser name/version, catalog version, status, started/completed timestamps, error code, output checksum.
- Every reparse creates a new row; the game points to the accepted current run.

`game_sides`: game, side identifier, display player name, preview known flag.

`game_pokemon`

- game side, stable within-game combatant key, canonical species/form when known, preview/selected/lead flags as nullable observations, linked team slot when confidently associated.

`battle_events`

- parser run, monotonic event sequence, turn, typed event kind, actor/target keys, canonical move/form where applicable, structured payload.
- P0 kinds: preview, bring/reveal, lead, move, switch, mega, faint, result. P1 adds damage, status, weather, terrain, ability, item, targeting, speed-order evidence.

`game_corrections`

- game, field path, typed corrected value, reason, actor, created/superseded timestamps.
- Views resolve effective values as correction over parser fact while retaining both.

`battle_sets`

- `id`, `user_id`, provider grouping key when present, best-of size, effective result, group confidence (`exact | strong | manual`), timestamps.

`battle_set_games`: set, game, game number, unique game membership. Set results are computed from member games unless explicitly corrected.

### Notes and knowledge

`notes`: `id`, `user_id`, subject type/id, Markdown source, sanitized render cache, created/updated/deleted timestamps. Allowed P0 subject types: team, team version, slot identity, game, battle set, matchup.

`opposing_sets`: reusable named sets with species/form, level, item, ability, nature, moves, EVs, mechanics, provenance, ruleset/catalog version, and completeness/uncertainty fields.

`opposing_teams`: persistent definitions composed through `opposing_team_members`; may originate from a game observation or user input.

`archetypes`: named reusable definitions, description, ruleset, and typed member/core criteria. Archetype workflows beyond basic reuse are P1.

### Matchups

`matchups`

- `id`, `user_id`, `team_id`, `last_validated_team_version_id`
- exactly one optional target: opposing team, archetype, or structured selected-opponent definition
- title, general plan, win conditions, threats/failure modes, turn-one options, notes, review state, timestamps.

`matchup_choices`

- matchup, kind (`preferred_lead | preferred_back | alternative_composition`), rank, label/notes.

`matchup_choice_slots`: choice, ordinal, user `slot_identity_id`; leads require exactly two slots and compositions must respect ruleset bring size. Backs may contain ranked individual slots or be part of a composition.

`matchup_games` and `matchup_calculations` link evidence. `matchup_dependencies` records the referenced team slot traits and validation state so new versions can produce precise warnings.

### Damage calculations

`saved_calculations`

- `id`, `user_id`, name, notes, optional matchup, ruleset, dependency mode, status, timestamps.
- Mode: `follow_latest | pinned_version | static_copy`. Each combatant stores its own source kind and reference; the calculation status is derived from both.

`calculation_inputs`

- calculation, revision, attacker/defender source descriptors and normalized resolved set snapshots
- move, attacker/defender levels/stages/status, field/weather/terrain/screens, doubles modifier, Helping Hand, critical hit, other versioned supported effects
- mechanics/catalog versions and semantic input checksum.

`calculation_results`

- input revision, engine name/version, raw integer range/distribution, HP and percentage range, KO summary/probabilities, assumptions/warnings, computed timestamp.

`calculation_dependencies`

- calculation, side, referenced team/slot/version or opposing set, watched field mask, last resolved version, state (`current | recompute_pending | outdated | invalid`).

Every recomputation appends an input/result revision; it does not rewrite the prior evidence snapshot.

### Operations and future providers

`jobs`: job kind, idempotency key, subject IDs, status, priority, available/lease timestamps, attempt/max-attempt counts, safe error fields, and correlation ID. Large/private inputs remain in their owned tables; the job row contains identifiers. Workers claim rows with a bounded lease and `FOR UPDATE SKIP LOCKED`. Exhausted work remains in terminal `failed` state for inspection and explicit retry.

`audit_events`: user/operator/worker identity, action, resource kind/ID, timestamp, request correlation, coarse change metadata; never raw private content.

`feature_flags` (P1): typed flag, environment, enabled/rollout configuration, author and audit timestamps.

`external_sources`, `external_sync_runs`, and provider-specific staging tables are P2. Canonical tournament records retain provider ID, retrieval time, URL, retained raw-source reference, and mapping provenance.

## Critical invariants

1. A `game.team_version_id`, once non-null and confirmed, cannot be silently changed by team edits; correction is an audited explicit action.
2. A sealed team version and its slots/moves/EVs cannot be updated or deleted while referenced.
3. A game belongs to at most one best-of-three set.
4. Duplicate provider replay IDs for a user resolve to the existing game/import item and never create another analytic fact.
5. Parser reruns append provenance and replace the selected parser interpretation transactionally; user notes/corrections are separate and survive.
6. All percentages are computed from stored integer numerator/denominator, never persisted as the only value.
7. A calculation result is unique by normalized semantic input checksum plus engine/mechanics version.
8. No cross-user reference is valid, including tags, notes, matchup evidence, calculation dependencies, and manual associations.
9. Unknown observations remain nullable/explicit unknown and do not satisfy true or false predicates.
10. Raw replay sources are retained at least as long as any associated game, subject to provider/legal deletion obligations.

## Indexing and partition strategy

Initial indexes cover ownership/time (`user_id, occurred_at`), team/version, normalized provider replay ID, import status, job status/availability/lease, set membership, canonical species IDs, and calculation dependency state. Analytics queries receive purpose-built composite indexes after `EXPLAIN ANALYZE` against a 10,000-game fixture.

Do not partition initially. Introduce time/provider partitioning only after measured table/index pressure; stable UUIDs and explicit ownership keep that migration possible.

## Deletion and retention

- Individual teams/games/plans/calculations use a short recoverable soft-delete period where references allow it.
- Account deletion disables access immediately, enqueues an idempotent database job, deletes live private records after the approved delay, and records only non-identifying audit proof.
- Backups expire on their documented schedule rather than being surgically edited; deleted data cannot be restored into live service without replaying deletion markers.
- Operational logs use short retention and never contain raw team/replay/note content.
- External cached data follows provider terms and can be purged by provenance.
